MASTER PROMPT — BUILD AND INTEGRATE THE COMPLETE LOGIN SYSTEM

You are working on an existing application. Your task is to implement and fully integrate a secure, production-ready authentication and login system into the existing project.

1. IMPORTANT: UNDERSTAND THE EXISTING PROJECT FIRST

Before making any changes:

- Inspect the entire existing project structure.
- Understand the current frontend, backend, database, API architecture, routing, and authentication-related code.
- Identify the existing Admin and User dashboards and their current routes.
- Identify how user roles and permissions are currently stored and managed.
- Reuse the existing backend, database, architecture, and components wherever possible.
- Do not create a separate application or an unnecessary parallel authentication system.
- Do not rebuild, redesign, or change the existing Admin or User dashboards.
- Do not modify existing Admin/User functionality, permissions, or business logic.

The Admin and User roles, permissions, responsibilities, and dashboard functionality have already been designed. Your job is to connect the login system to that existing structure.

2. LOGIN METHOD — EMAIL-FIRST PASSWORDLESS AUTHENTICATION

Implement a passwordless email OTP login system.

The login process must work as follows:

STEP 1 — Email Login Page

Create a clean, modern, professional login page.

It must contain:

- Application logo/name, using existing project assets.
- A welcoming heading.
- An email address input field.
- A Continue button.
- Appropriate email validation.
- Clear loading and error states.

The user enters their email address and presses Continue.

Do not ask for a password.

STEP 2 — Backend Account Identification

When the user submits their email:

- Send the email to the existing backend.
- Check the database for the account.
- Identify its existing role and account status.
- Determine whether the account is an Admin, Super Admin, or ordinary User.
- Check whether the account is active, blocked, or pending verification.

Do not expose the user's role or account existence through public API responses.

Use an appropriate generic response that does not reveal whether an email belongs to an Admin or ordinary User.

STEP 3 — Send Email Verification Code

Send a six-digit OTP verification code to the submitted email address.

Requirements:

- OTP must be generated securely on the backend.
- OTP must expire after 5 minutes.
- OTP must only be usable once.
- Store a secure hash of the OTP in the database, not the plain code.
- Resending a code must invalidate the previous code.
- Add resend cooldown and rate limiting.
- Limit incorrect verification attempts.
- Prevent brute-force attacks.
- Never expose OTP codes in frontend responses, logs, or production debugging output.

Use the existing email infrastructure if available.

If email delivery is not configured, integrate a suitable email delivery provider that fits the existing backend architecture. Keep credentials in environment variables and document the required configuration.

Do not use fake OTPs, hardcoded verification codes, or simulated successful email delivery in production.

STEP 4 — OTP Verification Page

After the user submits their email, display a dedicated verification page.

The page must include:

- Six-digit OTP input.
- Verify button.
- Resend code option.
- Countdown showing the OTP expiry time.
- Change email option.
- Loading, success, and error states.
- Clear messages for expired or incorrect codes.

The OTP input should support automatic progression between digits, paste of the complete six-digit code, and mobile-friendly keyboard behavior.

STEP 5 — Verify OTP and Create Session

When the user submits the OTP:

The backend must:

1. Validate the OTP against the stored hash.
2. Check expiry.
3. Check whether the OTP has already been used.
4. Check the account status.
5. Mark the OTP as consumed.
6. Create an authenticated session only after successful verification.
7. Return the authenticated user's identity and appropriate session credentials.

Use secure access and refresh token handling compatible with the existing application.

Where supported, implement refresh-token rotation, session revocation, logout, and expiration.

Store credentials securely. For a mobile application, use the platform's secure storage mechanism rather than ordinary local storage.
